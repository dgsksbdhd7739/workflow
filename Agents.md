### Dauerhafte technische Vorgaben
- Frontend: React + TypeScript + Vite, Tailwind CSS, React Router.
- Backend (seit 2.0.0, vorher Supabase): eigenes Node-Backend `server/` (Fastify, Node 24 führt TypeScript direkt aus) + PostgreSQL 17 auf dem VPS; Migrationen unter `server/db/migrationen/` (fortlaufend nummeriert, eingespielt von `server/scripts/migrieren.sh` als `postgres` beim `npm run deploy-server`). Frontend-Zugriff ausschließlich über `src/lib/backend.ts`. Tests: `cd server && npm run tunnel` (2. Terminal) + `npm test` gegen die Test-DB `workflow_test` — nie gegen `workflow`.
- **Backend-Betrieb:** systemd-Dienst `workflow-server` (Benutzer `workflow`, nur `/var/lib/workflow/dateien` beschreibbar), Geheimnisse in `/etc/workflow/server.env` (DB-Passwort, `JWT_SECRET`, `PROVISION_SECRET`, CORS-Ursprünge; optional `FIREBASE_DIENSTKONTO_DATEI` für Chat-Push). Nginx leitet `/api/` und den WebSocket `/api/live` auf `127.0.0.1:3000`, `/updates/` (Live-Update-Bundles) liefert es statisch aus. Nächtliche Sicherung `workflow-backup.timer` (03:15 UTC, DB + Dateien, 14 Tage, nur auf dem VPS selbst; Ergebnis in `/var/lib/workflow/sicherung.json`). Serverüberwachung ohne Zusatzprogramm: Das Backend misst jede Minute CPU/RAM/Platte/Netz nach `betrieb.messwerte` (8 Tage, Migration 0006, bewusst außerhalb von `public` und damit nicht über die Daten-API erreichbar); `GET /api/betrieb/serverzustand` nur für Plattform-Admins, angezeigt unter `/plattform-admin/server`. Keine Monitoring-Tools mit eigenem Web-Port installieren (z. B. Glances/Netdata ohne Auth) — die STRATO-Firewall lässt nur 22/80/443 durch. Ein `JWT_SECRET`-Wechsel meldet alle Nutzer ab.
- Android: Capacitor (`android/`). Windows: Tauri (`src-tauri/`).
- Android-Build-Toolchain: Gradle-Wrapper höchstens 9.5.x, solange AGP 8.x (`android/build.gradle`) im Einsatz ist — ab Gradle 9.6 wurde eine von AGP 8.x genutzte interne API entfernt, der Build bricht dann schon beim Konfigurieren ab (Android Studio schlägt das Wrapper-Upgrade trotzdem vor; nicht übernehmen ohne AGP-9-Umstieg). Kompilieren braucht JDK 21 (z. B. `JAVA_HOME` auf Android Studios `jbr`), ein System-JDK 17 reicht nicht (`invalid source release: 21`). Nach frischem Checkout zuerst `npx cap sync android`, sonst fehlt `android/capacitor-cordova-android-plugins`.
- Release-APK-Namenskonvention: `WorkFlow-v{versionName}.apk` (siehe `landing/index.html`) — kein anderes Namensschema verwenden.
- **Live-Update-Versionierung ist scharf:** `scripts/publish-update.mjs` veröffentlicht immer unter der aktuellen `package.json`-`version`. Der Update-Check auf dem Gerät (`src/lib/liveUpdate.ts`) vergleicht nur den Versions-*String* gegen das bereits installierte Bundle — wird ein Bugfix ohne Versionsbump erneut unter derselben Nummer hochgeladen, überspringen alle Geräte, die diese Nummer schon haben, den Download stillschweigend (kein Fehler, einfach kein Update). Vor jedem `publish-update.mjs`-Lauf zwingend `package.json`-`version` erhöhen — war die Ursache für einen echten Produktionsausfall (Projekt-Erstellung in der App durch stillstehendes Live-Update auf Vor-Rename-Code blockiert, siehe Version 1.4.3).
- **Neue APK ersetzt kein aktives Live-Update-Bundle:** Android behält App-Daten bei einem Update-Install (kein sauberer Neustart wie bei Erstinstallation). Hat ein Gerät bereits ein per Live-Update heruntergeladenes Custom-Bundle aktiv (`CapacitorUpdater.current()`), bleibt genau dieses nach dem Installieren einer neuen, frisch gebauten APK weiter aktiv — die neuen, in der APK gebackenen Web-Assets werden schlicht nie geladen, da `liveUpdate.ts` nur beim Start prüft und bei Versions-*Gleichheit* mit dem (alten) Manifest sofort abbricht. Deshalb bei jedem nativen APK-Rebuild **zwingend auch** `node scripts/publish-update.mjs` (mit aktuellem `dist/`) ausführen, sonst zeigen bereits installierte Geräte weiterhin den alten Stand, obwohl die neue APK korrekt installiert wurde (siehe Vorfall 2026-09-07, Version 1.5.0).
- **VPS am 2026-10-29 neu aufgesetzt** (Ubuntu 24.04, gleiche IP): Einrichtung ist jetzt reproduzierbar über `scripts/vps-setup.sh` (Updates + unattended-upgrades, ufw 22/80/443, SSH nur per Key, Nginx-Configs für sslip.io/`app.workflow-app.de`/`workflow-app.de`, Certbot für sslip.io ohne E-Mail-Registrierung). Neuer Deploy-Key `~/.ssh/workflow_vps_ed25519` (Kommentar `workflow-deploy`), der alte Key ist ungültig. Die APK-Location `/workflow.apk` aliast jetzt auf `/var/www/app/download/assets/workflow.apk`, der `Content-Disposition`-Dateiname steht in `/etc/nginx/snippets/workflow-app.conf` (bzw. im Setup-Skript). Die folgenden Angaben zur ursprünglichen Migration gelten ansonsten weiter. `VITE_API_URL` in `.env` muss für jeden Build gesetzt sein, der ausgeliefert wird (Web, APK, Tauri); `VITE_LOKALE_DEMO=false`.

Zugangsdaten in `.env`: `VPS_HOST`, `VPS_USER` (root), `VPS_SSH_KEY` (lokal unter `~/.ssh/workflow_vps_ed25519`, Public Key liegt auf dem Server in `~/.ssh/authorized_keys` — Passwort-SSH-Login ist auf diesem VPS deaktiviert, nur Key-Auth). ### Architektur-Vorgaben
- Multi-Tenant über `unternehmen_id` + Row Level Security; siehe `docs/firma-erstellen.md` für Firmen-Provisionierung.
- **RLS bleibt die einzige Quelle der Zugriffsrechte:** Das Backend führt Nutzeranfragen per `Datenbank.alsNutzer()` als Rolle `authenticated` mit `request.jwt.claims` aus (`auth.uid()` liest daraus). `alsDienst()` (service_role, umgeht RLS) nur für Anmeldung/Sitzungen und die geprüften Verwaltungsfunktionen in `server/src/funktionen/` — nie für Daten, die ein Nutzer anfordert. Die Daten-API gibt nur Tabellen in `public` mit aktivem RLS frei: neue Tabelle ohne RLS = über die API unsichtbar (gewollt). Neue RPC-Funktionen müssen in `RPC_FREIGABE` (`server/src/daten/routen.ts`) eingetragen werden, neue Speicherbereiche in `BUCKETS` (`server/src/dateien/routen.ts`) und per Migration in `storage.buckets`.
- Dateien: Berechtigung über die Policies auf `storage.objects` (Pfad-Ordner = Projekt-/Firmen-ID, Helfer `projekt_ordner_erlaubt()` usw.); Downloads nur über kurzlebige HMAC-signierte Links von `/api/dateien/:bucket/signieren`.
- Namen `auth.users`, `auth.uid()`, `storage.objects`, `storage.foldername()` sowie die Rollen `anon`/`authenticated`/`service_role` sind bewusst Supabase-kompatibel nachgebildet (`0000_rollen_auth_storage.sql`), damit die übernommenen Policies unverändert gelten — nicht umbenennen.
- DB-Terminologie folgt der UI: Tabellen/Spalten heißen `projekte`/`projekt_id` bzw. `aufgaben`/`aufgabe_id` (siehe Migration `0035_projekt_aufgabe_umbenennung.sql`).
- Gebäude werden als `gebaeude` mit erforderlichem `projekt_id` geführt, darunter `geschosse` und `einheiten` (Migration `0005`). Alle tragen `projekt_id`; zusammengesetzte Fremdschlüssel `(id, projekt_id)` erzwingen, dass ein Geschoss/eine Einheit im Projekt seines Gebäudes liegt, und dass Aufgaben/Termine nur Bereichen des eigenen Projekts zugeordnet werden. Zugriff für Lesen über `kunde_hat_zugriff(projekt_id)`, Schreiben durch Admin/Planer über `projekt_im_eigenen_unternehmen(projekt_id)`; neue geschachtelte Gebäudedaten müssen dasselbe Muster nutzen. Fortschritt/Status nie speichern, sondern aus Aufgaben/Terminen ableiten (`src/lib/gebaeude3d.ts`).
- 3D-Ansichten (three.js über `@react-three/fiber`/`drei`) nur per `React.lazy` laden, damit three.js nicht im Haupt-Bundle landet. Beschriftungen als `Schild3D` (Canvas-Sprite) statt `<Html>` aus drei — dessen eigene React-Wurzeln brechen unter React 19 beim Umschalten. Wechsel von `transparent` an einem Material nur über einen neuen `key` (three.js kompiliert sonst nicht neu).
- Gebäude aus Plänen (`src/lib/planAnalyse.ts`, Dialog `PlanAufbau`, Migration `0007`): läuft komplett im Browser mit pdfjs. Ebene aus dem Plantitel („Grundriss 3.Obergeschoss“, sonst Planname), Maßstab aus „1:50“-Texten, Außenumriss aus neutral-grau gefüllten Flächen (Wandschnitte) — dafür bekommt pdfjs einen Proxy-Zeichenkontext, der alles andere verwirft (nur `canvasContext` übergeben, mit `canvas` ignoriert pdfjs 6 den Kontext). Fenster/Türen werden per morphologischem Schließen überbrückt; unplausible Umrisse (Einheiten außerhalb, deutlich kleiner bei gleicher Zimmerzahl) übernehmen den Umriss darunter. Etagen werden über gemeinsame Achsbeschriftungen (mind. 2) übereinandergelegt. Einheiten = große Raumnummern bzw. FreeText-Anmerkungen. Gespeichert in Metern im Gebäudesystem (`geschosse.grundriss`, `plan_bild_pfad`/`plan_bild_lage` für das Planbild als Boden, `einheiten.lage_x/lage_z`). Räume (`geschosse.raeume`, Migration `0008`): zweite, feinere Wandmaske (5 cm) inkl. dunkler Linien ab 0,27 pt (Trockenbau ist oft nur als Linie gezeichnet; die echte Linienbreite wird beim Setzen von `lineWidth` mitgelesen, weil pdfjs dünne Striche auf 1 px verbreitert), Türen bis ~1,2 m geschlossen, nur innerhalb des Gebäudes. Raum→Einheit über Raumstempel „301.20 (301)“ im Raum, sonst nächstes Einheiten-Schild ≤ 4 m (Flure > 80 m² bleiben ohne). Wände 1:1 (`geschosse.waende`, Migration `0010`): Rasterrechtecke (5 cm). Seit 2.10.0 liest `src/lib/planVektoren.ts` den pdfjs-Operator-Strom selbst (`getOperatorList({ intent: 'print' })`, eigene CTM-/Farb-/Linienbreiten-/Strichelungs-Verfolgung, Pfade aus `constructPath`-DrawOPS) statt eines Proxy-Zeichenkontexts. Regeln: graue Füllung 30–85 % (+ 1-px-Kontur, sonst verschwinden Streifen-Schraffuren durch Kantenglättung), dunkle Kanten ≥ 0,27 pt, kräftig rote Linien 0,4–0,9 pt nur achsparallel (hellrot = Möbel, ≥ 0,9 = Beschriftungskästen, schräg = Hinweislinien) + rote Füllungen, nie gestrichelt; Schraffur = kurze (< 0,6 m) diagonale/punktförmige, unverbundene Striche ohne Bögen, nur bandförmig und zwischen Wandkanten; dünne Wände = parallele Linienpaare (≥ 1 m, 5–30 cm Abstand, an beiden Enden angeschlossen), erst innerhalb des Gebäudes. Grenze = Außenumriss + 15 cm; Flächen dicker als ~1,6 m und kompakte Teile < 0,3 m² fallen weg. Achsraster: Beschriftungen nur am Blattrand, per robuster Geradenanpassung bereinigt. Öffnungen bleiben Lücken. Tür- und Fenstererkennung wurde in 2.9.0 auf Wunsch des Nutzers entfernt (Migration `0011` löscht `tueren`/`fenster`) – Öffnungen bleiben Lücken im Wandraster, nichts hineindeuten. Flur = lang/schmal nach Außenmaß. Planbild je Etage/Gebäude ausblendbar (Ansichtseinstellung in localStorage). Planbild 1,25 cm/px (max. 8192 px, Mipmaps + Anisotropie); beim Heranzoomen zeichnet `PlanSchaerfe3D` den sichtbaren Ausschnitt aus der PDF nach (braucht `plan_bild_lage.blatt_x/blatt_z`, seit 2.7.0). Android-Zurück-Taste über `@capacitor/app` (`src/lib/zurueckTaste.ts`, natives Plugin – erst ab APK 2.7.0). 3D-Wände = Raum- und Umrisskanten als zusammengefasste Boxen (Aussparungen im Umriss scheitern, sobald ein Raum den vereinfachten Umriss schneidet).
- Pläne: `plaene.seite` wählt die Seite einer mehrseitigen PDF; mehrere Pläne dürfen dieselbe Datei nutzen (Löschen der Datei erst, wenn kein Plan mehr darauf zeigt). PDFs nur über `src/lib/pdfLaden.ts` laden (Zwischenspeicher je Datei, Zeichengröße über `begrenzterMassstab` gedeckelt). `src/lib/pdf.ts` ist der PDF-**Export** (jsPDF), nicht verwechseln.
- Nginx muss `.mjs` als JavaScript ausliefern (sonst blockiert der Browser den pdfjs-Worker); zusätzlich benennt `vite.config.ts` `.mjs`-Assets beim Build in `.js` um.
- Mit `VITE_LOKALE_DEMO=true` startet die App direkt in `LokaleDemo` ohne AuthProvider und zeigt ausschließlich Beispieldaten aus lokalem Gerätespeicher. Dieser Modus ist eine Entwicklungs-/Demooberfläche, kein Auth-Bypass und kein Ersatz für echte Nutzerdaten oder Synchronisierung; ohne den Schalter bleibt der normale geschützte App-Fluss unverändert.
- 2FA wird serverseitig erzwungen: `/api/auth/anmelden` gibt bei aktivem Faktor nur ein 5-Minuten-Zwischentoken, die Sitzung entsteht erst nach dem Code (`/anmeldung-bestaetigen` ist deshalb eine öffentliche Route, nicht unter `ProtectedRoute`).

## Dokumentationsprinzip

Bei jedem Arbeitspaket sollen folgende Artefakte synchron mitgeführt werden, sofern betroffen:
- betroffene README-/docs-Dateien (`README.md`, `docs/*.md`)
- in-App-Changelog (`src/lib/changelog.ts`) bei nutzersichtbaren Änderungen
- `Agents.md` bei bereichsübergreifenden Regel- oder Prozessänderungen
- `TODO.md` für offene Punkte

## Verbindlicher Agent-Arbeitsmodus

Diese Regeln gelten für jede Arbeitsanfrage in diesem Projekt.

Pflichtablauf pro Arbeitspaket:
1. `Agents.md` und `TODO.md` vor Beginn lesen, sie sind die verbindliche Arbeitsgrundlage für dieses Projekt.
2. Betroffene Bereiche identifizieren.
3. Zugehörige README-/docs-Datei im selben Arbeitspaket prüfen und bei Bedarf aktualisieren; falls für einen betroffenen Bereich keine Doku existiert, bei Bedarf neu anlegen.
4. Bei nutzersichtbaren Änderungen den in-App-Changelog (`src/lib/changelog.ts`) ergänzen.
5. Abschlussmeldung erst, wenn Code, betroffene Doku und Changelog synchron sind.
6. **Fokus-Regel:** Während der Bearbeitung höchste Konzentration auf Code-Integrität; keine unvollständigen Implementierungen hinterlassen.
7. **Integritätsprüfung vor Abschluss:** Vor jeder Abschlussmeldung Typecheck (`tsc -b` bzw. `npm run build`) und Lint (`npm run lint`) sauber durchlaufen lassen.
8. **Sprachvorgabe:** Antworten auf Deutsch, kurz und in Stichpunkten wo sinnvoll.
9. **Versions-Commit:** Nach einer bewussten Versionsänderung (neuer Eintrag im Changelog + `package.json`/`versionName`) Commit und Git-Tag (`vX.Y.Z` passend zur Version) selbstständig erledigen. **Push zu einem Remote wird vorher kurz angekündigt, nicht stillschweigend ausgeführt** — Ausnahme: der dokumentierte `/update`-Deploy-Workflow, der bereits vorab als voll-autonom autorisiert ist.
